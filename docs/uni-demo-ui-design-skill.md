# uni-demo UI / Design Skill

> 适用对象：`uni-demo` 项目的 AI Coding、前端开发、页面改版、工具页新增、首页视觉升级。
> 目标：让项目从“传统工具类小程序界面”升级为“更符合 AI 时代的原生工具工作台”。

## 1. 文档定位

本文件基于以下思路整理：

- Anthropic `frontend-design/SKILL.md`：强调页面必须有明确主题、独特视觉判断、非模板化设计选择。
- `impeccable`：强调可执行的设计命令、确定性检查、实时迭代，不让 AI 产出落回通用 SaaS 模板。
- `taste-skill`：强调 AI 产出不只是“能用”，而是要具备审美品味和克制感。
- `Awesome Design`：强调可以借鉴成熟产品的设计语言，但必须经过本项目语境重组。
- 动画类 Skill：强调动画必须服务任务流，而不是为“炫”而加。
- `Web to Figma`：强调优秀设计可以被拆解、重组、落地，不必从零想象。
- `ai-website-cloner-template`：强调可以借结构和节奏，但不能直接网页照搬到小程序。

这不是一个“网页炫技 Skill”，而是一个为 `uni-app + 微信小程序 + H5` 约束下的工具型产品定制的设计技能文档。

## 2. 项目北极星

### 2.1 一句话定位

`uni-demo` 不是“工具列表集合”，而是一个：

**会理解用户下一步动作的原生工具工作台。**

### 2.2 产品气质

应当避免两种常见误区：

- 误区 A：做成传统宫格式工具箱，只有入口，没有引导。
- 误区 B：强行做成聊天式 AI 壳子，和真实工具能力脱节。

推荐方向：

- 原生优先
- 连续处理优先
- 结果导向优先
- 轻智能感，而不是重聊天感

### 2.3 当前项目最适合的产品形象

建议统一成：

**聪明、克制、可靠、能预判下一步的效率型工具产品**

而不是：

- 通用 SaaS 后台
- 花哨营销站
- 纯视觉实验页

## 3. 设计总原则

## 3.1 Ground It In Subject

每个页面都必须先回答 3 个问题，再开始设计：

1. 这个页面服务什么具体任务？
2. 用户在什么场景下打开它？
3. 页面唯一最重要的动作是什么？

示例：

- 首页：帮助用户更快开始一次处理，而不是浏览全部工具。
- 二维码生成页：让用户尽快生成可保存、可继续加工的二维码。
- 磁力链接页：让用户把文本快速变成可继续操作的有效结果。
- 图鉴页：让用户高效检索、筛选、比较，而不是只看“好看卡片”。

如果页面无法回答这 3 个问题，设计一定会滑向模板化。

## 3.2 Hero Is Thesis

首页第一屏不能只是“标题 + 分类”。

首页首屏必须表达一个明确判断：

- 最近继续处理什么
- 现在最适合开始什么
- 哪条链路可以一键完成

首页的 Hero 更像“当前工作台”，不是“导航目录”。

## 3.3 Structure Is Information

结构必须反映任务关系，而不是装饰关系。

可以使用：

- 最近使用
- 推荐场景
- 连续链路
- 高价值工具
- 按任务阶段分组

应减少：

- 只有按工具类别平铺
- 纯粹按图标均匀排布
- 所有卡片权重完全一样

## 3.4 Spend Boldness In One Place

每个页面只允许一个“记忆点”。

例如：

- 首页：工作流 Hero
- 二维码页：结果预览区
- 图鉴页：强筛选器
- 阵容页：结构化人物组合视图

其余区域必须克制，不要每块都抢戏。

## 3.5 Motion Must Serve Flow

动效只能服务于：

- 页面进入
- 结果出现
- 继续下一步
- 状态切换

不要加入大量无意义漂浮、滚动视差、循环闪烁。

## 4. uni-demo 的产品级改版方向

## 4.1 首页从“工具分类”升级为“工作台”

当前首页结构更像目录页。后续应升级为四层：

1. Hero：最近继续 / 一键开始 / 推荐链路
2. 快捷工作流：如“磁力链接 → 二维码 → 图片打乱”
3. 高价值工具分组：媒体、图鉴、文本
4. 全量工具列表：作为次级信息

首页不应再把所有工具卡片放在同一视觉层级。

## 4.2 工具页从“单点功能”升级为“结果驱动页”

每个工具页建议拆成四段：

1. 输入区
2. 处理区
3. 结果区
4. 下一步建议区

其中“下一步建议区”是 AI 时代工具产品最关键的差异点。

例如：

- 磁力链接页结果区下方：生成二维码
- 二维码生成结果下方：图片打乱
- 二维码解析结果下方：磁力补全 / 图片打乱

## 4.3 图鉴页不走通用工具风

图鉴、阵容、角色详情不应沿用普通工具页视觉。

建议单独作为一个“子产品风格”：

- 更强的收藏感
- 更强的信息层级
- 更少工具化按钮堆叠
- 更强调头像、属性、星级、筛选、关系映射

## 4.4 登录和权限提示走“温和引导”

不主动骚扰，不抢首屏，不强制打断。

登录设计原则：

- 进入需要登录的功能时再说明原因
- 提供明确收益而不是空泛提示
- 登录入口始终可找到，但不压过主任务

## 5. 视觉系统建议

## 5.1 总体风格

建议整体视觉方向为：

**轻智能工作台 + 原生小程序质感 + 明确信息层级**

关键词：

- 清晰
- 轻锐
- 有呼吸感
- 少而准的强调

不建议走：

- 紫色渐变泛滥
- 玻璃拟态堆满
- 暗黑炫技
- 过度圆角卡片化

## 5.2 色彩规则

可采用“中性基底 + 每个工具域一条强调色”的策略。

### 基础中性色

- `#F5F7FB` 页面浅背景
- `#FFFFFF` 卡片背景
- `#0F172A` 主文字
- `#475569` 次文字
- `#CBD5E1` 弱边框

### 工具域强调色建议

- 图鉴：琥珀橙 / 赤金
- 媒体：青蓝 / 湖蓝
- 二维码：靛蓝 / 黑灰
- 文本：蓝紫 / 石墨
- 娱乐：深绿 / 亮绿

规则：

- 一个页面最多 1 条主强调色
- 状态色独立，不和品牌强调色混用
- 不要为了“AI 感”强上荧光绿或赛博紫

## 5.3 字体策略

微信小程序环境中，自定义字体成本较高，因此不强调外部字体资源，强调的是：

- 明确的字号层级
- 明确的字重差异
- 明确的字间距和留白

建议层级：

- Hero 标题：大、紧、稳
- 卡片标题：中等偏大，字重更强
- 描述文案：较短，避免废话
- 数据标签：更紧凑，更克制

原则：

- 不要让描述文案过长撑满卡片
- 不要所有标题都是一样粗一样大
- 工具型页面优先可读性，不追求网页杂志式排版

## 5.4 圆角和阴影

建议统一：

- 大卡片：`20-24rpx`
- 中卡片：`16-18rpx`
- 小按钮：`12-16rpx`

阴影规则：

- 阴影要轻
- 尽量用层级对比和背景对比替代重阴影
- 小程序内不使用过多大面积模糊阴影

## 6. 页面模板规则

## 6.1 首页模板

首页建议采用：

```text
┌──────────────────────┐
│ 顶部品牌 / 状态入口     │
│ 今日推荐链路 Hero       │
├──────────────────────┤
│ 最近继续               │
├──────────────────────┤
│ 推荐工作流             │
├──────────────────────┤
│ 高价值工具分组         │
├──────────────────────┤
│ 全量工具目录           │
└──────────────────────┘
```

首页不允许首屏直接进入“无差别卡片矩阵”。

## 6.2 工具页模板

工具页标准骨架：

```text
┌──────────────────────┐
│ 页面标题 / 简短说明      │
├──────────────────────┤
│ 输入区                 │
├──────────────────────┤
│ 主操作按钮             │
├──────────────────────┤
│ 结果区                 │
├──────────────────────┤
│ 下一步建议 / 连续处理    │
└──────────────────────┘
```

## 6.3 结果页模板

结果页必须具备：

- 结果预览
- 结果状态
- 主操作
- 次操作
- 下一步建议

不要只停在“成功提示 + 保存按钮”。

## 6.4 弹层模板

弹层适合：

- 补充式处理
- 不值得单独跳页的下一步操作
- 结果确认

弹层不适合：

- 复杂多步骤主流程
- 需要深滚动和大量说明的页面

当前项目里非常适合弹层化的功能：

- 二维码生成预览
- 图片打乱承接
- 轻量选择器

## 7. 文案 Skill

## 7.1 文案原则

文案要描述用户动作，不描述系统实现。

推荐：

- 生成二维码
- 保存图片
- 继续打乱
- 再解析一次

避免：

- 提交
- 开始处理任务
- 执行
- 调用转换能力

## 7.2 工具描述原则

首页工具描述要短、准、有使用感。

推荐风格：

- 粘贴解析并保存直链
- 自动补全并继续生成二维码
- 按密钥打乱图片

避免风格：

- 提供高效便捷安全稳定的处理能力
- 集成多种功能满足多场景需求

## 7.3 空状态和失败状态

空状态应引导下一步。

错误状态应说明：

- 出了什么问题
- 用户该怎么继续

避免模糊话术：

- 操作失败
- 未知错误

---

## 8. 动效 Skill

## 8.1 推荐动效

- 页面进入淡入 + 轻微上移
- 卡片分组顺序显现
- 结果区展开
- 按钮点击反馈更明确
- 下一步建议区在结果产生后出现

## 8.2 不推荐动效

- 首屏大段连续动画
- 背景持续漂浮
- 过多缩放和旋转
- 影响输入效率的过场

## 8.3 小程序约束

微信小程序优先：

- 使用简单 transform / opacity
- 控制动画时长
- 结果页重于装饰页
- 保证低端机不卡顿

## 9. 参考系统使用规则

## 9.1 如何参考 `Awesome Design`

允许参考成熟产品的：

- 节奏
- 分区
- 重点层级
- 信息组织

不允许直接照搬：

- 配色原样复制
- 文案原样复制
- 复杂网页组件原样复制到小程序

## 9.2 如何使用网页克隆思路

克隆不是目标，提炼才是目标。

正确做法：

1. 看对方首屏如何讲重点
2. 看对方结果区如何组织
3. 看对方如何引导下一步
4. 转换成适合小程序的原生结构

## 9.3 如何使用 `Web to Figma`

适合用于：

- 拆解优秀案例
- 看布局层次
- 观察视觉节奏

不适合用于：

- 把网页原封不动导成小程序设计稿

## 11. 确定性检查清单

每次 AI 产出页面后，至少自检以下项目：

1. 首屏是否一眼能看出页面唯一任务？
2. 页面是否有一个明确记忆点？
3. 是否仍然像“默认工具卡片模板”？
4. 结构分组是否反映真实任务关系？
5. 文案是否是用户动作语言？
6. 是否出现无意义渐变堆叠？
7. 是否出现过多阴影和圆角？
8. 是否所有卡片长得完全一样？
9. 是否给了结果后的下一步？
10. 是否存在只为装饰而存在的元素？
11. 动效是否服务流程，而不是炫技？
12. 小程序端是否可原生实现？
13. H5 和小程序是否都能接受这个布局？
14. 结果页的主按钮是否足够明显？
15. 次按钮是否没有抢主按钮？
16. 描述文案是否过长？
17. 空状态是否告诉用户能做什么？
18. 错误状态是否告诉用户怎么修复？
19. 是否过度模仿某个网页产品而丢失本项目语境？
20. 图鉴页面是否与普通工具页做出风格区分？
21. 首页是否体现“继续处理”而非纯导航？
22. 是否保留了当前项目的原生小程序优先原则？
23. 是否避免了一屏塞满所有信息？
24. 页面是否在暗色模式和移动端下仍然成立？

建议按这个顺序推进：

1. 首页
2. 二维码生成 / 解析 / 图片打乱链路
3. 磁力链接结果承接
4. 图鉴首页与详情页

- 不为了高级感牺牲可读性和操作效率

## 13. 最终判断标准

一个页面是否合格，不看它“像不像 AI 做的”，而看：

- 用户是否更快开始
- 用户是否更容易完成
- 用户是否更自然进入下一步
- 用户是否能记住这个页面

如果一个页面只是更花哨，但没有更好地承接任务，那就不符合本 Skill。
